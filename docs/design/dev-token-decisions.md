# Developer token implementation decisions

## 2026-10-16 — #1029 shared contract

- Use a new `DeveloperApiToken` credential: `pfd_` followed by 64 lowercase hex characters (32 cryptographically random bytes). It is distinct from `pfk_` and legacy `pkdev_`; it grants no legacy dev/payroll access.
- Permission enum is `READ_ONLY` or `READ_OPERATE`, immutable after creation. All selected deployments share that permission. API v1 enforcement is #1030.
- Owner-session management lives at `/api/developer-tokens`: GET lists, POST creates; `/[tokenId]`: GET inspects, PATCH atomically replaces `deploymentIds`, DELETE idempotently revokes. `/deployments` lists eligible selection candidates. Bearer credentials cannot manage tokens; sandbox sessions are explicitly refused.
- Create body: optional trimmed 1–64 character `label`, required `permission` and 1–100 unique UUID `deploymentIds` (normalized to lowercase before duplicate detection), optional integer `expiresInDays` 1–365 (omit for no expiry). PATCH accepts only `deploymentIds`, including an empty array to suspend all access. Permission, label and expiry are immutable; replace the credential to change them.
- Maximum 10 unrevoked, unexpired tokens per owner and 100 grants per token. Serialize management writes on the owner row; validate and lock eligible deployment rows inside the same transaction as the grant write. Owners may remove retiring/retired grants but cannot add or retain them in a replacement selection.
- Lists use UUID cursor pagination (default 20, maximum 100), ordered by immutable ID. Responses use `{ data: { items, nextCursor } }`; metadata is `{ id, tokenPrefix, label, permission, createdAt, lastUsedAt, expiresAt, revokedAt, deploymentIds }`. Only create additionally returns `token`. All successful responses set `Cache-Control: no-store`.
- Management writes share one owner bucket of 30 requests per minute; the static write-route guard recognizes only the explicit `requireDeveloperTokenManager(true)` call.
- Management audits are transactionally persisted with mutations, with IDs/permission only; no credential or hash. Revoked tokens and transaction attribution remain retained. Add nullable `SignedTransaction.developerApiTokenId` with a separate relation, leaving deployment attribution intact; runtime population is #1030.
- Add the user-authorized integration branch `dev-token` to existing CI branch triggers so child PRs receive the standard Node/Rust checks.

- API v1 bearer acceptance, mint-side `markTokenKnown`, cache correctness on grant/revocation changes, operation permissions and ApiRequestLog/reporting attribution remain #1030. This lifecycle change alone does not make `pfd_` usable against API v1.

## 2026-10-16 — #1030 API authorization and attribution

- API v1 accepts `pfd_` alongside existing `pfk_`; legacy `pkdev_` and session credentials remain rejected. Authentication returns an explicit `tokenType` discriminant and separate token owner/creator context. Every developer request rechecks token liveness, active non-sandbox owner, explicit grant, current ownership and confirmed ACTIVE deployment state.
- `GET /api/v1/deployments` uses the shared bearer, per-token rate, error and request-history wrapper. Both credential families may discover their own eligible scope. Response `{ data: { items: [{ id, flowName, network }], nextCursor } }`; cursor is an ID bound rather than a row lookup, default limit 20, maximum 100. Discovery returns no account, graph, wallet, contract configuration or unrelated deployment data.
- Every route declares its exact method/operation; coverage checks the declaration against the exported method and filesystem path. The published permission matrix treats reconciliation as operate. Known credentials still spend the per-token stable endpoint bucket when permission or grant checks refuse them. Existing funding GET/POST share their original endpoint allowance.
- A live developer credential refused for a missing grant remains known and does not acquire a negative cache entry. This preserves immediate selection edits and access to other selections. Unknown/revoked/expired/inactive credentials still use the existing bounded negative-cache/pre-auth behavior; known status always requires a database liveness check. Newly minted developer credentials are marked known.
- Preserve legacy rate/lease/wait keys. Developer credentials use a separate `developer:` ID namespace, including payout leases and concurrent waits; the token family and raw ID remain explicit in audit metadata. Existing payout lease deployment/hash checks, wallet consent, control intent deployment/action binding and durable work admission remain in force.
- Populate `SignedTransaction.developerApiTokenId`, never the deployment-token FK. Keep signer `userId` null for bearer callers, derive `callerAccountId`/audience from the developer owner, and retain first attribution across retries. A hash already recorded for another deployment/network fails before submission; same-deployment recovery remains available to authorized callers.
- Add nullable developer credential attribution to request-history records and reports. Old persisted queue records parse with a null default; keep `apiTokenId` semantics unchanged. Activation unions both token families; preparation/recovery joins match family, both token fields, account and deployment. Revocation/grant removal never deletes finality or attribution records.
- OpenAPI/Postman gain the discovery operation now to keep executable contract drift checks green; the broader integration guide/examples and SDK are still #1032/#1033. No product scope questions remain unresolved for this issue.
