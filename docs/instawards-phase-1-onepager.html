D1 · Real DEX swap

Soroban / Rust — extend + net new · Week 1

Wire the existing swapper to the Soroswap testnet router, unhide it in the builder, and produce a verifiable swap transaction. Today it fulfils swaps from a pre-funded balance — its own comment says “here we simulate.”

What gets built
  • Contract-to-contract authorization — authorize_as_current_contract so the router can pull asset_in. No crate here does this yet, and it is the one piece unit tests cannot prove.
  • The router call — quote via router_get_amounts_out, derive amount_out_min from slippage_bps, deadline-bounded, revert on shortfall.
  • parent + require_auth — swapper and yield are the only two pipeline contracts missing it, so receive_and_forward is callable by anyone today.
  • Constructor arity fix — scval.ts sends 6 args where Rust takes 5. Swap flows cannot deploy at all today; the same bug sits in yield.
  • Schema move — rateBps → slippageBps + routerAddress, with a migrateFlowGraph branch so saved flows still load. Router is an allowlist, never free text.
Done when a flow built on the canvas deploys to testnet and a triggered swap routes through the real Soroswap router — verifiable on stellar.expert, not a mock.

D2 · Partner-drivable API

TypeScript / Next — extend + net new · Week 2

Today Paiflow is a thing people use. D2 makes it a thing software uses. Payroll already has a machine interface, but it is one-off and payroll-specific.

The v1 surface
Execute POST /api/v1/deployments/[id]/execute — relayer-signed, no user signature at request time
Events GET …/events — cursor-paged, reusing the payroll (occurredAt, id) cursor
Tokens Hashed, per-deployment. Closes open security issue #247
Wrapper withApiV1 — auth + rate limit + audit, extracted from payroll
Docs OpenAPI + Postman, hand-written — no spec tooling exists in the repo

Load-bearing decision: the swapper has no execute entrypoint and the relayer cannot call it directly. The one path that works fronts the flow with a webhook contract, whose execute_escrow needs only relayer auth: the user pre-funds once, the partner then fires swaps with no signature. Zero contract changes — but the endpoint executes a pipeline, not a swapper.

Done when an authenticated curl from outside the app causes a real swap on testnet and returns a tx hash, and the events endpoint pages through that deployment's events.

D3 · Reusable builder inputs

React / TSX — extends shipped code · Week 3

The builder ships today. This deliverable is consolidation, not construction: 14 node types and 14 hand-written config forms live in one 2,800-line file, each inventing its own way to ask for an amount, an address, or a percentage.

What gets built

AmountInput and ShareInput are new — hand-rolled at 8 sites and copy-pasted verbatim twice. AssetSelect is an extraction of an existing file-private component; AddressPicker already ships and is used 7×. A jsdom + RTL component harness has to exist before any of it can be tested.

Design posture
  • Test harness first. A .test.tsx is not collected by the current runner — it reports green having run nothing. Prove CI goes red before trusting it.
  • Build four, adopt what fits. The Swapper panel has no amount field, so AmountInput is proven only if adoption widens to the split panel. Name that choice.
  • Lossless bps. The split's share input rounds 5 bps to 10 — reused as-is on slippage it silently doubles the user's tolerance.
Done when the Swapper panel renders shared primitives, error markup is consistent, and component tests run green in CI on a runner that collects them.

D4 · Validation package

Video · guide · evidence — net new · Week 4

The Chapter Lead does not review pull requests. They review evidence, against the grid in SOW §6.2 — which carries a row for this package alongside D1–D3. Work finished in the repo but unevidenced is, for this award, not finished.

Artifacts
  • 3–5 min technical demo video — published, cross-linked from the repo.
  • Integration guide — curl examples and sample XDR payloads. Written during D2: if they are painful to write, the API is painful to use.
  • Receipt list — every tx hash on Stellar Expert, plus contract and WASM hashes.
  • Screen recordings — deploy, trigger, and the API-driven swap.

The numbers it carries: ≥5 unique flows · ≥6 distinct wallets · ≥60 on-chain events · ≥5 swapper executions · ≥1 WASM uploaded · live testnet URL. Most of the counting is already automated by /admin/submission-proof — three added counts finish it.

Done when the Chapter Lead can verify all four rows of §6.2 without asking a follow-up question.
