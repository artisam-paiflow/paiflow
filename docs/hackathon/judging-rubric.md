# Judging rubric reference

Internal organiser reference · October 30, 2026

Transcribed from the `Rubric` tab and checked against the scoring formulas in `Aklan Judges Scoring.xlsx`. This preserves the workbook's descriptions and scoring levels without requiring access to the local Excel file. It contains no team scores or judge identities.

The [event primer template](event-primer-template.md) uses these five criteria and weights. The workbook's recorded-demo cap is preserved below as a source rule; the template still requires organisers to publish the event's demo-scoring policy. Do not apply an unpublished distinction to participants.

## Criteria and weights

| Criterion               | Weight | What judges look for                                                                                                  |
| ----------------------- | -----: | --------------------------------------------------------------------------------------------------------------------- |
| Problem and user        |    15% | A specific user with a clear, believable problem. Claims are specific and proportionate.                              |
| Solution and creativity |    20% | Addresses the problem in an original way, and paying feels natural to the user.                                       |
| Impact on Stellar       |    10% | Real use of Stellar and credible adoption potential. Demonstrated results are kept separate from future potential.    |
| Paiflow integration     |    30% | The flow fits how money should move and Paiflow is central to the app, not bolted on.                                 |
| Works end to end        |    25% | Shows the customer payment and a verifiable payout to the intended recipients. Recorded demo: score no higher than 3. |

## Scoring

Each judge selects a level from 1 to 5 for all five criteria. Calculate that judge's score out of 100 as:

```text
score = sum(level × weight_percentage) / 5
```

For example, level 4 in every criterion gives 80/100. Average the scores of judges who completed all five criteria; incomplete scorecards are excluded, not counted as zero. If no judge has completed a scorecard, leave the final score blank.

The workbook ranks final scores from highest to lowest and gives equal scores the same rank. It does not resolve ties; organisers must settle any tie-break policy separately.

## Scoring levels

### Problem and user (15%)

| Level | Description                                                          |
| ----- | -------------------------------------------------------------------- |
| 1     | No clear user or problem.                                            |
| 2     | Vague user or problem, or overstated claims.                         |
| 3     | Clear problem, but the user is generic or the need is assumed.       |
| 4     | Specific user with a clear, believable problem.                      |
| 5     | Specific, well-evidenced problem, ideally validated with real users. |

### Solution and creativity (20%)

| Level | Description                                                                         |
| ----- | ----------------------------------------------------------------------------------- |
| 1     | Does not address the stated problem.                                                |
| 2     | Partly addresses the problem; conventional idea with an awkward payment experience. |
| 3     | Addresses the problem with a familiar approach; payment experience is workable.     |
| 4     | Addresses the problem well with original elements; paying feels natural.            |
| 5     | Original solution that fits the problem closely; paying feels seamless.             |

### Impact on Stellar (10%)

| Level | Description                                                                            |
| ----- | -------------------------------------------------------------------------------------- |
| 1     | No clear role for Stellar.                                                             |
| 2     | Stellar is used, but its role or impact is unclear.                                    |
| 3     | Clear use of Stellar with modest, plausible activity.                                  |
| 4     | Stellar is central, with a credible path to useful activity or adoption.               |
| 5     | Strong, credible adoption case; demonstrated results clearly separated from potential. |

### Paiflow integration (30%)

| Level | Description                                                              |
| ----- | ------------------------------------------------------------------------ |
| 1     | Paiflow is missing or not connected to the app.                          |
| 2     | Paiflow is bolted on; the flow does not match how money should move.     |
| 3     | Working integration; the flow partly fits the problem.                   |
| 4     | The flow fits how money should move and is central to the app.           |
| 5     | The flow fits the problem precisely and Paiflow is essential to the app. |

### Works end to end (25%)

| Level | Description                                                       |
| ----- | ----------------------------------------------------------------- |
| 1     | No working demo.                                                  |
| 2     | Partial demo; the payment or payout is not shown.                 |
| 3     | Payment shown, but the payout is incomplete or not verifiable.    |
| 4     | Live payment and payout shown, with minor issues.                 |
| 5     | Smooth live demo of the customer payment and a verifiable payout. |

## Recorded-demo rule in the source workbook

For **Works end to end**, the workbook caps a recorded demo at level 3/5, equivalent to at most 15 of that criterion's 25 weighted points. Other criteria retain their full ranges. This cap does not mean every recording earns level 3; judges still assess the evidence shown.

Before using this rule for an event, state it in the participant primer's demo-scoring policy and align the judges' worksheet. The current template adopts the weights only; its demo-scoring policy remains a placeholder.
