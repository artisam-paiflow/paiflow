## What a user can do when this is done

A partner's backend holds a token scoped to one deployed flow. It asks the API to prepare an
execution of that flow, signs the returned transaction with its own key, submits it, and polls a
second endpoint to watch the resulting on-chain events. No Soroban knowledge, no access to
anything beyond that one flow, and a funded Stellar key of its own to sign with — the API never
signs.

## Scope notes

Eight points where the work differs from the SOW's wording. Each is a deliberate choice, checked
against the code and the SOW's own architecture before the sprint, and recorded here rather than
by editing the SOW, which is fixed as approved. Where the reason is security it says so; where it
is not, it says what it is.

**1. Execute is two calls, and the partner signs.** The SOW has `POST …/execute` execute the
swapper in one call and the API return "signed/submitted transactions" (§3.2 l.107, §3.7 l.183,
§3.8 l.199–200, §4.1 l.243, §5.1 l.284). Here `POST …/execute` returns the **unsigned** deposit
transaction; the partner signs it with its own key and posts it to `POST …/execute/submit`.
_Why — security, and the SOW's own architecture:_ §3.10 (l.224–225) says "the operator's wallet
signs it (keys never touch the server)". A one-call execute that returned a signed transaction
would need the server to hold a partner's key. With two calls a leaked API token can only prepare
and relay what the partner signed; it cannot move funds by itself. §5.1 Week 4 (l.286) already
asks for "sample XDR payloads", which exist only in this shape. curl cannot sign, so the
transcript is curl → `stellar tx sign` → curl. _Verify:_ the curl transcript in the evidence pack
shows the unsigned envelope returned, signed locally and submitted; the swap is on stellar.expert.

**2. New deployment-scoped tokens rather than the payroll credentials.** The SOW says "extend the
existing payroll developer API" (§3.7 l.176–177) and "extract … primitives from the existing
payroll endpoints" (§4.1 l.243, §5.1 l.284). Here a new `DeploymentApiToken` is stored as a
sha256 hash, shown once, revocable and optionally expiring; the user-scoped developer token is
refused on `/api/v1`, and the payroll routes keep their paths. The shared `DEV_API_SECRET` this
note was written against was refused here too, and was removed from the product altogether on
20 September (#247), which also narrowed every payroll and `dev-*` route to owner-scoped reads.
_Why — security:_ the payroll shared-secret path dropped the deployment ownership check, so
extending it literally would have inherited that. A token bound to one deployment limits a leak to
one flow and can be revoked without touching anything else. The primitives themselves already
existed; what is new is the composition and the scoped credential.
Moving the payroll routes is the "splitter and streamer API expansion" §4.1 excludes. _Verify:_
the generic-refusal cases in `tests/unit/api/v1/auth.test.ts`; no payroll route moved.

**3. A route-handler wrapper, not edge middleware.** The SOW says "into a shared `/api/v1`
middleware" (§5.1 l.284). Here every v1 handler is wrapped in `v1Route`
(`lib/api/v1/handler.ts`), and `middleware.ts` gains one line. _Why — defence in depth, and a
runtime constraint:_ the app's `middleware.ts` runs on the edge runtime, which cannot query the
database for a token. Authenticating inside the handler also means a path-pattern mistake at the
edge can never open a route by accident. _Verify:_ the wrapper and its tests; `middleware.ts`
gains one pattern.

**4. Execute runs the flow's deposit trigger; the swapper runs as the next step.** The SOW says
"`POST …/execute` for the Swapper action" (§4.1 l.243, §5.1 l.284). _Why — it keeps the SOW's own
re-entrancy property (§3.9):_ the swapper's `execute_step` requires its parent's authorization, so
nothing outside the pipeline can invoke it, by design. The API therefore executes a swapper
_flow_, and all copy says so. _Verify:_ the submit route refuses any envelope that is not a single
`deposit` on this deployment's trigger contract; stellar.expert shows the swap sub-invocation.

**5. Rate limits are keyed on the token, not the caller's IP.** The existing trigger routes key
their limits on the client IP. _Why — security:_ the IP comes from the first `X-Forwarded-For`
hop, which a caller controls, so an IP-keyed limit is advisory. A token-keyed limit is
enforceable. _Verify:_ the 429 case in `tests/unit/api/v1/handler.test.ts`.

**6. Events are read from the app's own record, not straight from the chain.** The SOW says the
"event polling endpoint returns on-chain events" (§5.1 l.284). Here the endpoint pages forward,
oldest first by `(ledger, eventId)`, over the events the app has decoded for the deployment's
contracts, with an opaque cursor; freshness comes from the submit path, which records a
transaction's events immediately, and the one-minute poller. _Why — reliability, not security:_
the network's `eventId` is the single key, so a partner never sees a duplicate, and a partner
polling every two seconds cannot fan out into Soroban RPC load. The events are a subset of what
the chain emits, up to about a minute behind it; the guide says so. _Verify:_
`tests/unit/api/v1/events.test.ts`; the latency note in the [developer guide](../../api/README.md#4-poll-events).

**7. The OpenAPI document is hand-authored.** The SOW says "generate an initial OpenAPI spec"
(§4.1 l.243). Here it is a TypeScript object, served at `GET /api/v1/openapi.json` and committed
as JSON. _Why — no new dependency:_ no generator or YAML parser is installed, and every addition
is gated on a clean dependency audit. A drift test gives the guarantee a generator would.
_Verify:_ `tests/unit/api/v1/openapi.test.ts` fails if a v1 route has no entry, an example stops
matching its schema, or the committed copy falls behind.

**8. Anyone can drive the API anonymously, through a demo token rather than the sandbox.** The SOW
asks for "a public testnet URL anyone can open, try, and inspect" (§3.8 l.193–194) and a "public URL
where the API is active" (§6.1 l.298). `GET /api/v1/openapi.json` and `POST /api/v1/demo-token` are
both public and need no token; the second returns a 60-minute deployment token for one shared,
operator-provisioned swapper flow on testnet, so the execute and events endpoints can be driven from
a cold start. _Why the sandbox identity is still refused — security:_ it is disposable and
unauthenticated, so a machine credential it minted would outlive it with no owner to revoke it. The
demo token inverts that — it is owned by an ordinary account, it expires in an hour, and the route
that issues it is off by default and cannot be enabled under `STELLAR_NETWORK=mainnet`. _Verify:_
`curl -X POST https://paiflow.xyz/api/v1/demo-token` returns a `pfk_` token and a deployment id;
the events endpoint with no bearer still returns 401;
[Trying the API](../../api/README.md#trying-the-api) is the three-command walkthrough and
[`evidence/d2/`](../evidence/d2/) holds the original transcript and the Postman capture.

Also a security choice, though not a deviation: `execute/submit` parses the signed envelope and
refuses anything but a single `deposit` invocation on this deployment's trigger contract, so a
token for one flow cannot submit an arbitrary signed transaction under that flow's audit trail.

### SOW starting point, checked against the code

The SOW's description of where the code stood (§3 item 2, l.64–69) was written before the code
was surveyed on 13 September. These are corrections of fact, not decisions:

- The swapper never used the `dev-*` endpoints (l.66). It has no dev variant; those routes mutate
  the splitter, payer, subscription and cash-out dev contracts. It used `trigger`,
  `submit-trigger` and `tx-status` only.
- The `dev-*` routes are not only "shared-secret authenticated" (l.67); they also accept a
  user-scoped developer token or a session. As of 20 September (#247) those two are the only
  rungs left — the shared secret was removed.
- "No cursor-based event polling endpoint" (l.68–69) held for **contract** events only. The
  payroll event feeds already paginated by cursor over payroll-domain events.
- "No deployment-scoped API token model" (l.67) was accurate for API tokens; per-deployment
  secrets already existed on the deployment record (the webhook secret and the charge token).
- "No documented curl examples" was accurate: the only `curl` in the repository was inside the SOW.
- §3.9's risk table has no row for the developer API. The mitigations are scope notes 2, 3 and 5
  and the envelope check; the [week-2 report](../week-2.md#decisions) adds the row.
- "Endpoint tests green in CI" (§5.1) means unit and mocked-RPC tests; CI has no end-to-end job.
  The testnet run is outside CI.
- §6.2 lists a "Deliverable 4" that does not exist.

## Found in the close-out audit

The deliverable was audited against the SOW, the code, the evidence pack and the public app on
18 September before it was closed. Every requirement held and every deviation was already
recorded above. Two things the audit found are tracked rather than absorbed, because neither
changes what the SOW asks for:

- **The audit trail records successes only** (#547). The "audit primitives" of §4.1 write
  `API_EXECUTE_PREPARED`, `API_EXECUTE_SUBMITTED` and `API_EXECUTE_CONFIRMED`; a submit that the
  network rejects, a swap that reverts on-chain, or an envelope refused by the trigger-contract
  check leaves no row. The §6.1 "sample audit log entry" is the success path and is present; a
  partner probing a token, or one whose swaps keep reverting on slippage, is invisible in the
  owner's log until the failure actions exist.
- **Two evidence files are maintained by hand** (#548). `08-openapi.json`, "the document as
  served", is a copy of the committed specification that nothing asserts against it, and it is
  only literally as served once the commit that changed the specification has been promoted to
  the public app. This has since happened: #554 added the demo-token route to the committed
  specification on 19 September without refreshing the snapshot, so the two now differ by that
  route, its schema and one sentence of the description. The snapshot is kept as a dated
  18 September copy rather than rewritten, and every link to it says so. `tests/e2e/d2-api-testnet.spec.ts`, which would produce the pack's optional
  `10-e2e-*` files, has not been run; the evidence run was the hand-driven curl sequence in the
  transcript.
