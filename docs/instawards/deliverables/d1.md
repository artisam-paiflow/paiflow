# D1 — Real-DEX swapper

> **Statement of Work, Deliverable 1.** Integrate the existing swapper contract end to end so
> that it performs a real swap through the Soroswap testnet router, expose it in the visual
> builder, and produce a verifiable swap transaction. Full wording in the
> [Statement of Work](../../instawards-phase-1-sow.md), section 4.1.

**Target week:** 1 (7–13 September) · **Status:** Complete — all four evidence items the SOW
asks for exist and are public: the Swap block is live on [paiflow.xyz](https://paiflow.xyz), a
swap flow deployed from the public app has swapped through the Soroswap router on testnet, the
swapper WASM hash resolves on testnet, and the deploy-and-trigger journey is screen-recorded.
Updated 11 September.

## What a user can do when this is done

Open [paiflow.xyz](https://paiflow.xyz), drag a **Swap** block onto the canvas, choose the
asset going in and the asset coming out, set a maximum slippage, deploy to Stellar testnet,
and send funds in. The contract swaps them on a real decentralised exchange and forwards the
result to the next step in the flow. Every step is verifiable on stellar.expert.

## Scope notes

Four points where the engineering work is narrower or wider than the SOW's wording. They are
recorded here rather than by editing the SOW, which is fixed as approved.

**The router is not user-selectable.** The SOW says "router selector". The panel shows a
single, read-only option, and the actual address is supplied by the server at deployment time.
A free-text address field would let a user point a flow at an arbitrary contract, and every
existing flow would break the next time Soroswap redeploys its testnet router.

**No new asset type.** The swapper trades the assets Paiflow already supports, using the live
XLM / USDC pool. Supporting exchange-issued tokens would have touched the asset model, payment
links and notifications, and was judged too wide for a 30-day sprint.

**One output.** A swap block has at most one downstream step. Splitting a payment several ways
is the splitter block's job, and combining the two is a normal flow.

**Public access is a sandbox session, not a shared account.** The SOW asks for a public testnet
URL where the Swap block is usable. Rather than publish a shared login, the login page mints a
disposable sandbox identity per visitor, limited to the builder, deploy and deployment views
and to pipelines the visitor's own wallet signs end to end. Reviewers get the block with no
account; the platform's own signer is never exposed to an anonymous session.
