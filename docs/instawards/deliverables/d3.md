## What a user can do when this is done

The Swapper panel is built from the four shared inputs the SOW names, each with the same
labelling, the same validation and the same error messages. Two asset selects, `Asset In` and
`Asset Out`, pick the pair. A share input, `Max slippage (%)`, sets the maximum slippage. Under
**Preview**, an amount input, `You send`, sets the size the live quote is asked for, and the quote
shows the expected output as its figure with the minimum the contract will accept underneath. A
collapsed **Advanced** section holds the address picker, which shows the Soroswap router the flow's
funds pass through (shown, not chosen — the server pins it), and the deadline. It opens by itself
when the deadline has an error or the router is not configured, so a problem is never hidden. The
panel is usable with a keyboard and on a phone.

## Scope notes

Three points where the work is narrower than the SOW's wording. Each narrows a risk, not the
scope: all four named components are rendered in the Swapper panel, every D3 clause has an owner,
and nothing the SOW asks for is dropped. They are recorded here rather than by editing the SOW,
which is fixed as approved. Where the reason is security it says so; where it is not, it says what
it is.

**1. The router is shown, not chosen.** Carried from D1. The SOW asks for `AddressPicker` in the
Swapper panel (§4.1 l.244) and for the builder to "select … `router`" (§3.2 l.103–104).
`AddressPicker` is adopted in a read-only pinned mode, under Advanced, that shows the router's
contract id with a copy button and a stellar.expert link. The graph has no router field; the server
supplies the router at deploy time (`lib/stellar/deploy.ts:155-162`). _Why — security:_ an editable
router would let a flow send its funds through an arbitrary contract. D1 recorded the same choice
([D1 scope notes](d1.md#scope-notes)), and showing the real contract id is more transparent than
the D1 panel's disabled one-option select (`d3/12`). _Verify:_ `d3/16`;
`tests/unit/swapper-pipeline.test.ts:260`, "…leaves the router off the graph"; no `router` key in
`SwapAction` (`lib/flows/schema.ts:364-380`).

**2. Slippage is the share input, and the amount input sizes the quote and stores nothing.** The
SOW asks for `AmountInput` and `ShareInput` in the Swapper panel (§4.1 l.244). Both are rendered.
`ShareInput` is `Max slippage (%)`, a percentage stored as basis points; its share-of-total
remainder line is off, because a swap has one output. `AmountInput` is `You send` under Preview: it
sets the size of the live quote and is UI state only
(`components/builder/panels/swap-panel.tsx:41-43`). _Why — security and stability, the contract is
not touched:_ the swapper swaps whatever arrives and has one output, so a stored amount or share
would be a constructor change, a breaking ABI change (CLAUDE.md §8) that would replace the WASM hash
D1 evidenced and reopen the contract D1 validated on testnet. Quoting at the user's own size is
also a safety gain: price impact grows with size, so a quote fixed at 10 units can look healthy for
a flow whose real deposits break a tight slippage bound (pool reserves on 21 September: 3,941,589
XLM / 416,520 USDC). _Verify:_ the four imports at `swap-panel.tsx:8-12`;
`tests/unit/builder/panels/swap-panel.test.tsx:287`, "keeps the preview amount out of the graph";
the recording at 2:20; no D3 commit touches `contracts/` or `SwapAction`'s fields.

**3. The two cross-field swap rules live in the deploy gate, not in a Zod refinement.** The SOW
says "unify Zod validation schemas" (§4.1 l.244). This is met for the schemas: the swapper flow's
Zod schemas (`SwapAction.slippageBps`, the quote query, the builder trigger amount) share one set
of primitives in `lib/flows/primitives.ts`. The exception is the two rules that compare fields,
that the assets differ and that slippage clears the pool fee. They are written once in
`swapConfigIssues()` (`lib/flows/swap-rules.ts:41`, called at `lib/flows/validate.ts:704`) rather
than in a `superRefine` on `SwapAction`. _Why — reliability, because it prevents lost edits:_
`PATCH /api/flows/[id]` parses the graph before it saves (`app/api/flows/[id]/route.ts:31`), so a
cross-field rule inside the Zod shape would reject every autosave while the user is mid-edit and
drop their other edits. The rules lose nothing: the server enforces them at
`/api/flows/:id/validate` and again inside `/api/deployments/prepare`, which every deploy passes.
_Verify:_ `tests/unit/flows/swap-rules.test.ts:143`, where a same-asset swap parses and is refused
by `validateFlow`; `tests/unit/api/deploy-prepare-swap.test.ts:167`, where the prepare route
refuses it with a field error on `Asset Out` and prepares nothing (#649).

## Implementation choices

Three clauses the SOW leaves open, and how they were met. None is a deviation — the wording does
not prescribe an approach, and each is recorded so a reader knows which one was taken.

**Component tests run in CI; the accessibility and phone spec runs outside it.** The SOW asks for
component tests and "UI tests green in CI" (§5.1 l.285). The jsdom component tests run in CI's node
lane on every change. The axe and Pixel 7 Playwright spec, the accessibility and mobile _pass_,
runs locally and against paiflow.xyz; the SOW does not ask for it to be a CI job, and no end-to-end
lane exists yet (CLAUDE.md §12, §19). The four new test packages are devDependencies only, never reach the shipped bundle, and
`pnpm audit` stayed as it was. _Verify:_ the `dom` project in
[`21-vitest-junit.xml`](../evidence/d3/21-vitest-junit.xml); `tests/e2e/d3-swap-panel.spec.ts`.

**The pass and the adoption are the Swapper panel's.** The SOW scopes D3 to the Swapper panel and
excludes "full builder-wide UI refactoring" (§4.1 l.244, l.262–263). The shared inputs are adopted
in the Swapper panel, and the axe scan covers it. What the panel sits in is shared by every node
type, so it was fixed once rather than forked: the config panel container (keyboard open, Close,
focus return, a docked sheet below 768px), reduced motion on the canvas edges (#647), the issue
flattening in four routes (#610), and `AddressPicker`'s file, whose existing callers keep their
behaviour (#609). Two later changes improved the builder around the panel — a focus ring on canvas
nodes and edges with Skip to canvas (#677), and a one-row phone header (#679) — without taking on
the mobile builder as a whole (#62). What the survey found in other panels is filed for a later
phase (#615–#620, #663). _Verify:_ `tests/e2e/d3-swap-panel.spec.ts` on both Playwright projects,
including the edge packet's `animationName` under `reduce` (`:436-443`); the unmigrated Pay panel,
[`18`](../evidence/d3/18-pay-panel-legacy-desktop.png).

**The deadline is a fifth field on the shared building blocks.** The SOW names four components for
the Swapper panel (§4.1 l.244), and the panel renders all four. It also has `Deadline (seconds)`,
a small `DeadlineInput` that belongs to the panel and is built on the shared `Field`, `inputClass`
and `useDraftNumber`, so it labels, validates and reports errors the same way. _Verify:_
`swap-panel.tsx:132-178`.

## Beyond the SOW

Added while building; the SOW does not ask for these.

- **The server enforces the asset catalogue the panel offers.** One catalogue feeds both
  `AssetSelect` and a `validateFlow` rule for swap nodes, and a `PENDING:` issuer is a field error
  rather than a 500. Before the sprint the restriction was client-only, so the API or the AI editor
  could save a swap on an arbitrary token. XLM/USDC is the only pair verified on the pinned router

## Props contract

What another node type's panel passes to adopt each component, read from the source in
`components/builder/inputs/`. Every component is controlled: the caller owns the value. The two
numeric inputs hold a draft while the user types and call `onChange` only with a value the flow
schema accepts, clamping on blur and saying so under the field; `AddressPicker` does the same with
`commit="valid"`. `error` is the message to show under the field, wired to `aria-invalid` and
`aria-describedby` through the shared `Field`. Each component has one test with a non-swap props
shape.

**`AssetSelect`** (`asset-select.tsx`) — `label`, `value: Asset`, `onChange(asset)`, `error?`,
`hint?`, `expectedAsset?` (the asset arriving from upstream; options that differ are disabled),
`options?` (defaults to the catalogue), `disabled?`, `onUpstreamCustom?: "adopt" | "error"` (what
to do when upstream delivers an asset outside `options`). Non-swap test:
`tests/unit/builder/inputs/asset-select.test.tsx:149`.

**`AmountInput`** (`amount-input.tsx`) — `label`, `value` (stroops as a string, `""` when unset),
`onChange(stroops)`, `asset?` (the unit suffix and the echo), `min?` and `max?` (stroops, defaulting
to 1 stroop and the largest i128), `decimals?`, `error?`, `hint?`, `disabled?`, `emptyNote?` (the
note shown when a cleared field blurs), `echo?` (the `= 1.5 USDC` line). Non-swap test, a pay
node's amount: `tests/unit/builder/inputs/amount-input.test.tsx:201`.

**`ShareInput`** (`share-input.tsx`) — `label`, `value` (integer basis points), `onChange(bps)`,
`minBps?`, `maxBps?`, `error?`, `hint?`, `disabled?`, `remainingBps?` (what is left of 100% once
every other share is counted; when given, the field shows the remainder and flags an
over-allocation as its error). Non-swap test, one of a splitter's shares:
`tests/unit/builder/inputs/share-input.test.tsx:89`.

**`AddressPicker`** (`address-picker.tsx`) — a union of three shapes:

- **Unlabelled:** the editable props below, with `error?: boolean`, which colours the border while
  the caller renders the message.
- **Labelled:** the editable props, plus `label`, `hint?` and `error?` (a string is shown under the
  field and described; a boolean only colours the border).
- **Pinned:** `pinned: { id, label, network }` and `hint?`. A server-supplied address shown read-only
  with a copy button and an explorer link; the Swapper's router uses it.

The editable props are `value`, `onChange(value)`, `placeholder?`, `pending?`,
`accept?: "account" | "contract" | "either"`, `pendingAllowed?`, `commit?: "always" | "valid"`,
`addressBook?`, `addressBookLoading?`, `addressBookError?`, `onAddressBookChange?` and
`onSelectEntry?`. Non-swap test, an account field with an address book and a picked entry:
`tests/unit/builder/inputs/address-picker.test.tsx:225`.

`PercentBpsInput` (`percent-bps-input.tsx`) is `ShareInput`'s internal core, not a fifth public
component: only `share-input.tsx` imports it.

## What "before and after" means here

The improvement is standardisation, not decoration. When the SOW was written, each node type in
the builder implemented its own inputs, and the page described "two different asset selectors in
the same file, adjacent to each other"; the survey found them to be two wrappers of one component
(see [SOW starting point](#sow-starting-point-checked-against-the-code)), but validation did behave
inconsistently and error messages did vary. The after state is one set of components in the
Swapper panel with one validation path.

A screenshot pair of the same panel looks similar at a glance, so the evidence also shows the
change in the code (the swap markup removed from `config-panel.tsx`, the swapper flow's schemas on
shared primitives, one rule function for the swap rules and one error model) and, for contrast, a
panel that has _not_ been migrated. That contrast is also the argument for adopting these
components across the rest of the builder in a later phase, which this sprint explicitly does not
attempt. [The code-diff note](../evidence/d3/20-code-diff.md) is that evidence: each claim with the
command that proves it.

## Decisions recorded while building

- **The config panel container (#613).** The container is shared by every node type, so its
  keyboard, focus, reduced-motion and docked-sheet changes apply to all of them. The axe scan
  covers the Swapper panel only. The 44px touch-target check covers the Swapper panel and, since
  #661, the editable `AddressPicker`'s controls on the Pay panel, because the Swapper renders only
  the pinned branch and the editable one had never been measured.
- **Chat and sheet on a phone.** Below 768px the config panel docks as a bottom sheet and the Ask AI
  chat is full-width, so only one is shown: selecting a node collapses the chat, and opening the chat
  dismisses the sheet.
- **What axe scans.** `[data-testid="config-panel-container"]`, the region around
  `[data-testid="config-panel"]`, so the header's Close and Delete buttons are scanned too.
- **The builder no longer overflows a phone.** The canvas column's bare `1fr` track grew to the
  toolbar's content width (560px on a 412px Pixel 7 with the D3 test flow; the figure varies with
  what the toolbar holds), which put the docked sheet's buttons off screen. The track is now
  `minmax(0, 1fr)`; desktop is unchanged, since the content already fitted there. At first the
  toolbar rows wrapped on a phone; since #679 the phone header is a single row whose title
  truncates instead.
- **Checked by hand on a real phone** (Playwright's device emulation has no virtual keyboard): on a
  vivo Y22s (Android 14, Chrome), `Max slippage (%)` stays visible above the keyboard and the page
  does not zoom on focus

  [`13-phone-meta.json`](../evidence/d3/13-phone-meta.json)).
- **The simplified Swapper panel (#670).** After the rebuild the panel was still hard to read: six
  fields at equal weight, two to four lines of help under each, every label and hint in the pink-tinted
  `on-surface-variant`, and the live quote as small grey prose at the bottom. #670 changed its presentation
